# AME INT32 GEMM 现场演示 150 秒讲者稿

目标：让观众看到同一份 C 核心确实生成 AME 指令，在 Spike 执行后得到正确矩阵。
演示环境为 x86_64 Linux；目标程序为 RV64 裸机。不要把 Spike 宿主时间描述为硬件性能。

## 会前准备

提前完整执行一次 `bash scripts/acceptance.sh`，检查全部正例和负控。
终端字号调到后排可读，切到 `~/ame-tutorial-gcc`，打开
`examples/gemm_kernel.h`。现场命令生成新的 `build/live-*`，不会覆盖以前的运行结果。

## 0 到 25 秒 说明任务与配置

“这个例子把两个 4×4 的 INT32 矩阵相乘。主路径使用 RV64、UDS32、16 个 M 和
4 个 Acc 资源，硬件 tile 边长 N 为 4。输入包含负数且不对称，方便发现符号和转置错误。
今天展示编译、指令、执行和校验四个环节。”

## 25 到 65 秒 解释核心代码

显示 `examples/gemm_kernel.h`：

“先从普通 C 数组加载 A、B，把零矩阵送入累加器。接着调用矩阵乘累加接口，
最后把累加结果搬回 M 并存入数组。这里的 `1x1` 表示一块基础 tile，
在 N=4 时包含 16 个 INT32 元素。C++ 使用同一组 typed intrinsics。”

## 65 到 110 秒 现场编译与执行

运行：

```bash
bash scripts/present.sh
```

“这条命令现在用包内 GCC 和 Binutils 重新构建 ELF，再由修复后的 Spike 执行。
执行结束后先检查完成 PC、资源配置、ownership、状态以及输出边界，
再用宿主 Python 独立计算全部 16 个结果。不是只看进程返回码。”

命令完成后指出 `PASS` 及矩阵第一行 `-10 71 26 38`。
如果机器较慢，缩短下一段到 20 秒，保留运行过程，不假装缓存输出是现场执行。

## 110 到 140 秒 对照实际指令与校验

脚本最后显示 `mls.rm`、`mmov.a.m`、`mmulacc.2d`、`mmov.m.a`、`mss.rm`。

“这些来自刚刚执行的 ELF。接口名与助记符不一定完全相同，
例如 `mcopy_m2a` 对应这里的 `mmov.a.m`。左上结果为
`1×2−2×7+3×6−4×4=−10`，其余元素也逐项核对过。”

## 140 到 150 秒 引导自学

“交付包里提供 C/C++、O0/O2 的完整验证，以及故意破坏一个结果的负控。
教程可以继续查看反汇编、修改输入、排查诊断，也可以从冻结源码重新构建全部工具。”

## 现场出现失败

不要把 FAIL 或超时跳过后宣称运行成功。终端会显示失败阶段及错误详情。
可以在 Notebook 的执行与排错章节查看命令、反汇编及数值差异。
若使用会前生成的 `build/` 内容继续讲解，应明确标为“预跑结果”。
现场运行不需要联网，前提是配套工具已安装完成。
